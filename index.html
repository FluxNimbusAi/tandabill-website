The problem, in three lines

Invoice goes out. Payment promise hangs in a chat thread. Neither side wants to move first — one risks paying, the other risks working.

And when it's not two parties but a group — a trip, a lease, a shared table — the same escrow law runs the split: one verified human per seat, payouts pulled with proof.

How a TandaBill settles

  1. Create the bill Invited seats join a contract — payer and payees, each with a World-verified wallet.
  2. Escrow funds Payment locks into the contract (USDC on World Chain), releasable only by the agreed settlement terms.
  3. Record the work Expenses and delivery events attach to the same bill — one ledger, both sides see it.
  4. Confirm & execute Every seat confirms the settlement state; only then does the contract release funds.
  5. Claim with proof Each payee pulls their payout; the on-chain event is the receipt nobody can argue with.

The mechanics that make it safe

Checks-effects-interactions

Payout state is committed before any token transfer, so a malicious or reverting token hook can never re-enter and double-pay. Proven by golden re-entrancy tests, not asserted by comment.

Pull-based claims

Execute computes payouts; each seat claims its own. A failed claim stays retryable — no silent stranding of a payee's funds.

Hard settlement windows

Confirmation runs on a bounded window (1 h production pace); if a roster never confirms, refundSettlement releases escrow back after the max-hold — money can't sit frozen forever.

Adversarial-token hardened

USDT-style tokens that return nothing on success won't revert; tokens that lie with false surface as typed errors. Both behaviors are pinned by tests against hostile token doubles.
